# E4-F4-S1 Define a versioned multi-role persistence schema

## User Story

As a product maintainer, I want a versioned persistence schema for color roles so that URLs and files can evolve without silently corrupting saved configurations.

## Related Epic

- [E4](./E4.md) - Multi-role tonal color system epic.

## Related Feature

- [E4-F4](./E4-F4.md) - Multi-role URL and import/export persistence feature.

## Scope

- Define one canonical serialized model containing schema version, surface configuration, primary configuration, and relevant preview settings.
- Decide which UI state is durable, including the active editing tab, without serializing transient hover or open-popover state.
- Add validation and normalization at the persistence boundary.
- Define migration from the existing unversioned single-color payload into the surface role with a default primary role.
- Share the schema and migration logic between URL and JSON workflows.

## Acceptance Criteria

- A documented typed schema represents both color roles and durable preview settings.
- Invalid or unsupported data is rejected without partially mutating application state.
- Existing single-color data migrates to surface and receives a valid default primary configuration.
- Serialization is deterministic for equivalent application state.
- Unit tests cover validation, normalization, version handling, and legacy migration.
